Objective 2: Event Correlation – Testing Report

1. Introduction

This report presents the testing and evaluation of Objective 2: minimising the volume of security events forwarded to a Security Information and Event Management (SIEM) system through pre-correlation.

The event correlator processes aggregated authentication events generated by Objective 1. It filters non-alert records, groups related security alerts by host and source IP address, and combines related alerts occurring within a configured 15-minute correlation period into incidents. Original event records are retained as supporting evidence.

2. Test Environment

Testing was conducted in the Cisco DEVASC Ubuntu virtual machine using Python 3.8.2.

The main implementation file was event_correlator.py. The application reads JSON Lines input, validates event records, performs correlation and generates SIEM-ready output and a correlation report.

The production input is output/aggregated_events.jsonl.

The outputs are:

output/siem_ready_events.jsonl

output/correlation_report.txt

3. Functional Testing

3.1 Integration with Objective 1

The event correlator was tested using the actual aggregated authentication events generated by Objective 1. It successfully processed two valid records, filtered one non-alert record and retained one alert record. One incident was produced, with no invalid records.

The 0% reduction was expected because only one alert record was available for correlation.

3.2 Correlation of related alerts

Three related alert records associated with the same host and source IP address were used to test incident consolidation. The records fell within the configured correlation period.

The application combined the three alert records into one incident representing 12 failed login attempts. The original event records were retained as supporting evidence. This produced a 66.67% reduction in alert records.

3.3 Separation of unrelated alerts

Alerts associated with different host and source IP combinations were tested to ensure unrelated activity was not incorrectly combined.

The application produced two incidents from three alert records, achieving a 33.33% reduction. This confirmed that correlation respected the host and source IP grouping criteria.

3.4 Correlation time-window boundary

The time-window logic was tested using events at the correlation boundary and events outside it.

Events within the permitted 15-minute period were combined, while events outside the period were kept in separate incidents. This confirmed that the configured time-window condition operated as intended.

4. Error-Handling Testing

Error-handling tests assessed the application's response to invalid and incomplete input records.

The test dataset contained three records: one valid JSON event, one malformed JSON record and one JSON record missing a required field.

The application processed the valid record and skipped the two invalid records without terminating unexpectedly.

Results:

This demonstrated that the application could handle malformed and incomplete input while continuing to process valid records.

6. Evaluation and Limitations

The tests demonstrate that the event correlator can validate input records, filter and group alerts, consolidate related events and preserve supporting evidence. The performance test also demonstrated a substantial reduction in the number of records produced for downstream processing.

However, the performance dataset was synthetically generated. The measured reduction demonstrates the application's correlation capability under controlled conditions rather than a verified reduction in the workload or financial cost of a live SIEM platform.

Furthermore, the application has not been connected to a live SIEM environment. Actual SIEM ingestion costs, resource consumption and operational performance have therefore not been measured.

7. Conclusion

The functional, error-handling and performance tests demonstrate that the event correlator performs the principal requirements of Objective 2. It consolidates related security alerts into incidents, preserves original event evidence, handles invalid input records and reduces the volume of alert records produced for downstream processing.

In the performance test, 1,000 alert records were consolidated into 20 incidents, representing a 98% reduction, with a measured processing time of 0.033133 seconds.

Final integration testing using Objective 1's production output confirmed that both objectives operate together as an integrated workflow. The results provide evidence that the application has achieved the intended pre-correlation functionality within the scope of the project.
Mock SIEM Webhook Integration Test

A mock SIEM webhook was implemented to evaluate whether the event correlator's JSONL output could be transferred to and accepted by an external SIEM-style endpoint. The test used a temporary local HTTP server to simulate the receiving application without requiring a live SIEM deployment.

The test loaded the generated SIEM-ready incident records, converted them into a JSON payload and submitted them to the mock webhook using an HTTP POST request. The receiving endpoint validated the JSON payload and returned an HTTP 200 response with an acceptance status and the number of records received.

The test passed when the receiving endpoint accepted the payload and the number of records received matched the number submitted. This demonstrated successful transfer and acceptance of the generated incident data within the controlled test environment.

The test was limited to a local mock endpoint. It did not establish a production connection to a SIEM platform or demonstrate encrypted transmission. A production implementation would require HTTPS, appropriate authentication and secure handling of endpoint configuration.
